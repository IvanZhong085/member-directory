# 會員資料更新與維護表單・架構規劃

> 本文件是「會員自助更新資料」「名錄維護追蹤」「Bug 回報區」三件事的架構規劃，經問答定案後撰寫，
> 並經過對照程式碼的逐條查證（限流數字、上限、既有機制的行為描述皆以現行程式為準）。
> 目標讀者：要實作這個功能的人（或 AI），以及日後想了解「為什麼這樣設計」的維護者。
> 尚未實作——這是規劃文件，不是使用說明。

### 為什麼這個組合對會員最簡單

- 會員端只有兩件事，都不用帳密：**改資料 → 點連結填表單**；**看到問題 → 按「回報問題」打幾個字**。與報名參訪、新夥伴申請的體驗一致。
- 把關成本放在組長端（審核更新），彙整成本交給機器（排程整理 Bug），網管只在「升級建議」產出時才需要看。
- 錯誤資料不會直接上站（兩段式），冒名申請靠「組長認得自己組員」擋下——這是分會（實體組織、人人互識）才有的低成本身分驗證。

## 整體架構

沿用現有「新夥伴申請」已驗證可行的管線，**平行複製一條**，不共用佇列：

```
會員（免帳密）
  │ 填 Google 更新表單（只填想改的欄位）
  ▼
表單回應試算表 ←──────────────┐（永遠留底，送失敗可人工補救）
  │ onUpdateFormSubmit 觸發器  │
  ▼                           │
Apps Script（伺服器端，密鑰不外洩）
  │ POST {secret, update:{…}} 到 Worker /update
  ▼
Cloudflare Worker /update（限流、清洗、樂觀鎖）
  │ 追加一筆到 data/_updates.json（更新待審區）
  ▼
組長登入後台 → 「更新待審」清單 → 變更前後對照 → 核可／退回
  │ 按「發布到網站」（走既有 /publish，權限與版本偵測不變）
  ▼
data/<組代號>.json 更新（蓋 updatedAt）＋ _updates.json 移除該筆
  ▼
GitHub Action（sync.yml）→ data.js / m/ 分享頁 / roster.csv 全自動重建
```

對照現有機制：`data/_pending.json`（新夥伴待認領）怎麼運作，`data/_updates.json`（更新待審）就怎麼運作。差別只在：pending 是「整個人新增」，updates 是「指定成員的部分欄位變更」。

Bug 回報是**另一條獨立通道**（站上按鈕 → Worker `/report` → `data/_bugs.json` → 排程 Action 整理），見「三、Bug 回報區」。

### 為什麼開新佇列檔，不共用 `_pending.json`

- `_pending.json` 有 `MAX_PENDING=50` 的容量上限，且與新夥伴申請共用同一個限流池；混用會互相排擠額度。
- 兩種資料語意不同（新增 vs 部分變更），共用一檔會讓認領 UI 和驗證規則都長出分支。
- 代價是 Worker 要把新路徑加進三處白名單（見下方「Worker 端」），一次改齊即可。

## 一、會員自助更新（表單 → 待審 → 核可）

### 1. Google 表單設計

**身分區**（比對用，不做技術驗證）：

| 題目 | 型式 | 必填 |
|---|---|---|
| 你的分組 | 下拉選單（12 組，含代號＋組名） | ✔ |
| 你的姓名 | 簡答 | ✔ |
| 所屬公司（同名時區辨用） | 簡答 | － |

**更新區**（與名錄欄位一一對應，全部選填；題目文字需與程式的別名表同步）：

行業／職稱、服務項目、適合引薦對象、我有…、我要…、25 秒自我介紹 Slogan、所屬公司、主要營業項目、公司網站——**9 題文字題**（新夥伴表單的 10 題扣掉姓名，姓名移到身分區且題目文字不同），沿用 `NEWMEMBER_Q` 的標題與別名機制。

> ⚠ 「所屬公司」會出現**兩題**：身分區的標題固定為「所屬公司（同名時區辨用）」，只進 payload 頂層的 `company`（身分比對用）；更新區沿用 `NEWMEMBER_Q.company` 的標題「所屬公司」，進 `fields.company`（申請更改用）。兩個標題經 `normTitle_` 正規化後必須不同，否則挑值時會對錯題——實作時要驗證這一點。

**照片區**（上傳題，全部選填）：形象照 1 張、名片 1 張、商品照最多 5 張。

表單說明文字必須寫明兩條規則：

> 「**只填你想更改的欄位，沒填的欄位維持現狀**。若要清空某欄，請在該欄填『無』，組長審核時會處理。」

已知取捨：

- Apps Script 無法程式化建立上傳檔案題，三個照片題要**手動**在表單編輯頁加上，標題須與程式一字不差（與新夥伴表單相同的限制與作法）。
- 表單含上傳題時 Google 強制填答者登入 Google 帳號——順勢**開啟 email 收集**（`setCollectEmail`），把填答者 email 一併送進待審資料，給組長多一層「是不是本人」的佐證。這是新夥伴表單沒做、更新表單要做的差異點。

### 2. Apps Script（tools/google-form.gs 擴充）

新增（與新夥伴表單平行、互不干擾）：

- `createMemberUpdateForm()`：建表單＋回應試算表＋掛觸發器。防重跑用**新的**指令碼屬性鍵 `UPDATE_FORM_EDIT_URL`（`guardAlreadyCreated_` 直接重用；但 `forgetForms_` 的鍵清單目前寫死兩個舊鍵，**必須加入新鍵**，否則重建表單的逃生路是斷的——已列入實作清單）。
- `onUpdateFormSubmit(e)`：組 payload、POST 到 Worker `/update`。觸發器名稱獨立，不與 `onNewMemberSubmit` 混用。
- `checkUpdateFormSetup()`：比照 `checkNewMemberSetup` 的診斷手法（故意送空 payload，用錯誤碼區分密鑰不符／未設定／線路通）。

直接重用、不必重寫：標題正規化與別名對應（`normTitle_`／`pickByTitle_`）、整條照片管線（`driveImageDataUrl_` → `thumbBlob_` → `blobToDataUrl_`，含 HEIC 轉檔與 650KB 上限）、`RELAY_URL`／`INTAKE_SECRET` 指令碼屬性機制。

需小改才能重用：照片歸檔——`archiveSubmissionPhotos_` 把子資料夾名「新夥伴照片」寫死在函式內，要把它做成參數，更新表單的照片才能歸到「會員更新照片/」。

payload 格式（**只含有填的欄位**——留空＝不更動就是在這裡實現的）：

```json
{
  "secret": "<INTAKE_SECRET>",
  "update": {
    "group": "A1",
    "name": "王小明",
    "company": "小明企業",
    "respondentEmail": "xxx@gmail.com",
    "fields": {
      "services": "冷氣保養\n舊機回收",
      "tagline": "新的一句話標語",
      "image": "data:image/jpeg;base64,…"
    }
  }
}
```

送出失敗（Worker 掛掉、密鑰錯）時只寫 Logger，**回應仍留在試算表**當備份，可人工補登——與新夥伴表單相同的保底設計。

### 3. Worker 端（worker/publish-relay.js 擴充）

新增 `/update` 端點，行為比照 `/intake`，差異在目標檔、資料形狀與兩處補強：

| 項目 | 設計 | 依據 |
|---|---|---|
| 認證 | 共用 `INTAKE_SECRET`（兩條通道信任等級相同：都只有 Apps Script 伺服器端持有）。未設定＝整條通道關閉（fail-closed） | 沿用 /intake 的密鑰哲學；若日後要單獨關閉更新通道，再拆成獨立 `UPDATE_SECRET` 即可 |
| 限流 | 同 IP 15 分鐘 20 份，**KV key 用獨立前綴 `update:`**，不污染登入與 intake 的計數 | /views 灌爆 KV 額度的教訓：公開端點必限流、必隔離 |
| 清洗 | 新寫 `sanitizeUpdate()`，規則見下 | 上限數值比照 `sanitizeApplicant`，但**迭代邏輯不同** |
| 識別碼 | `uid` 由**伺服器**產生（`u_` 開頭），外部不能指定；表單資料裡**沒有任何欄位能決定成員 id**（id 會變成 `m/<id>.html` 檔名，有路徑穿越風險，對應交給後台審核時做） | pid 由伺服器產生的同一原則 |
| 寫入 | 讀 `data/_updates.json` 現行內容＋blob sha → 追加 → 帶 sha 寫回；stale 就重讀重併，**最多嘗試 5 次（首次＋4 次重試，沿用 `MAX_INTAKE_TRIES=5` 的計數方式）**，全失敗回錯不靜默覆蓋。上限 `MAX_UPDATES=50`，滿了回 `updates_full` | /intake 的樂觀鎖 read-modify-write 迴圈 |
| 大小防線 | **追加後把檔案內容換算成發布用的 base64 長度，超過 3.5MB 即回 `updates_full`、不寫入**（與 `/publish` 的 `MAX_DATA_B64_CHARS` 同一把尺、留 0.5MB 餘裕）——這是 /intake 沒有、/update 必須補的一道（原因見「待審區資料格式」） | 防止佇列檔長到後台清不掉 |

`sanitizeUpdate()` 的規格（「留空＝不更動」在 Worker 層的實現，**不能照抄 `sanitizeApplicant`**）：

- **只迭代 `update.fields` 裡實際出現的鍵**。`sanitizeApplicant` 會把所有欄位物化成 `""`／`[]`，照抄會讓沒填的欄位以空值進佇列，後台核可時把人家的資料整批清空——正好打穿「留空＝不更動」。
- 清洗後為空的鍵（空字串、空陣列、不合格的照片）**直接剔除**；`fields` 清完變空物件時整筆退回 `bad_update`。
- 各欄上限比照 intake 現行值：一般文字與清單項 400 字（預設值）、姓名與職稱 80、公司 120、網址 300 且須 http(s) 開頭、清單 12 項、單張照片 base64 ≤700KB。唯一比 intake **嚴**的是**全部照片加總 ≤2MB**（intake 是 3MB；此額度只算照片，文字另計）——原因見「待審區資料格式」的膨脹計算。超出照片額度的照片欄比照 intake 剔除（該欄視同未填、不更動），試算表留底可人工補救。
- `group` 必須存在於 `_index.json` 的組代號、`name` 必填。

路徑白名單要**同步改齊三處**（漏一處就是發布被拒或驗證缺口）：

1. `DATA_PATH_RE`（Worker 與 admin.js **各有一份**，兩邊都要加 `_updates`）。
2. `canWriteDataFile`：`_updates.json` 比照 `_pending.json` 對所有組長開放寫入（核可後要從清單移除該筆）。這延續現有的知情取捨——組長之間看得到彼此組的待審項目，真正的把關在「核可寫入分組檔」那一步，而那一步的路徑權限不變。
3. `checkDataFileBody`：新增 `_updates.json` 的結構驗證——必須是陣列、每筆 `uid` 過 `MEMBER_ID_RE`、`group` 為字串、`fields` 為物件且陣列欄位型別正確、筆數 ≤50。驗證的目的是**保護後台佇列解析與 uid 的後續使用**（uid 會進 DOM 屬性與對應流程），並防止佇列被塞壞資料；`_updates.json` 不進合併產線（見下），壞掉不會凍結前台，但會讓待審區掛掉。

### 4. 待審區資料格式（data/_updates.json）

```json
[
  {
    "uid": "u_a1b2c3d4",
    "at": "2026-08-09T12:34:56.000Z",
    "group": "A1",
    "name": "王小明",
    "company": "小明企業",
    "respondentEmail": "xxx@gmail.com",
    "fields": {
      "services": ["冷氣保養", "舊機回收"],
      "tagline": ["新的一句話標語"],
      "image": "data:image/jpeg;base64,…"
    }
  }
]
```

- `fields` 只含會員有填的欄位；多行文字在 Worker 端切成陣列（與 intake 相同）。
- 照片在待審階段一律以 `data:` URL 內嵌，**核可並發布後**才由既有的 extract-inline-photos 產線轉成 `images/` 實體檔——未核可的申請不會在 repo 留下孤兒圖檔。
- **檔案大小是實質風險，上限之間有陷阱**：後台 `/publish` 對資料檔有 4MB 的硬上限（`MAX_DATA_B64_CHARS`，量的是「發布時整份檔案再 base64 編碼後」的長度，**只在 /publish 端檢查**；/intake 寫入時不驗檔案總大小）。佇列檔本身已含 base64 照片字串，發布時整檔再編碼會**膨脹約 4/3**——檔案在磁碟上約 3MB 就會頂到 4MB 上限。若佇列檔長過頭，組長核可／退回後**發不回去**，佇列從後台清不掉、形成死鎖。所以 `/update` 要兩道一起擋：**單筆照片加總 ≤2MB**（保證最大單筆放得進空佇列——2MB 照片的單筆檔案約 2.1MB、發布編碼後約 2.8MB，仍低於自檢線）＋**寫回前以發布同一把尺自檢 ≤3.5MB**（保證佇列檔永遠發得回去）。兩個數字若設成一樣（例如都 3MB），最大單筆會連空佇列都放不進去——這是設計時實際踩過的算術陷阱，留在這裡提醒。`_pending.json` 實測一筆含照片的申請就 1.5MB，這不是理論風險；接近額度的單筆會佔掉佇列大半空間，組長要勤清佇列。

### 5. 後台審核 UI（admin.js 擴充）

比照「新夥伴待認領區」整套渲染與事件模式，新增「**更新待審區**」：

- **清單**：每筆一張卡，顯示申請人自報的組別＋姓名＋公司＋email＋申請時間。
- **成員對應**：後台用「組別＋姓名」在現有名錄找人——唯一命中就預選；同名多筆或找不到時，卡片顯示該組成員下拉選單請組長**手動指定**。表單資料永遠不直接決定成員 id。
- **變更前後對照**：對 `fields` 裡的每個欄位，顯示「現在的值 → 申請的新值」。這是審核 UI 的核心——組長一眼看出這筆改了什麼，沒改的欄位不出現。
- **操作**：「核可」＝把 `fields` 逐欄套進該成員卡＋蓋 `updatedAt`＋從待審清單移除；「退回」＝僅從清單移除（表單回應試算表永遠留底，不怕誤刪）。都是本機草稿，**要按「發布到網站」才真正生效**（兩段式不變）。
- **權限**：viewer 整區隱藏；組長預設只看到自己組的待審申請（依 `group` 欄位過濾），總管理員看全部並可改派組別（處理會員選錯組的情況）。
- **一致性**：undo 快照與草稿目前寫死為 `{data, pending}`，必須擴充成 `{data, pending, updates}`，否則核可後按「復原」會遺失待審狀態；發布 payload 的逐字比對、`baseHashes` 版本偵測，都要把 `_updates.json` 一併納入（作法與 `_pending.json` 完全相同）。
- **序列化**：核可寫入分組檔時走既有的 groupBody 序列化與鍵順序，避免產生無意義 diff 或壞掉合併產線。

併發行為（照實描述，兩端機制不同）：**收件端**（/update）stale 時自動重讀重併重試；**後台發布端**（/publish）stale 時直接回 `stale_base` 錯誤擋下（前端認的是錯誤碼，不是 HTTP 狀態碼——預檢不符是 409、寫入時撞到是 502），由組長重新整理後再發，不自動重試。結論相同——會員送更新撞上組長發布**不會互蓋**，只是解法一個自動、一個由人重來。

清空欄位的處理：會員在表單填「無」時，該欄會以字串「無」出現在對照畫面，由組長核可時人工把該欄清掉——規則簡單、不需要程式猜語意。

### 6. 前台入口（site-config.js＋成員內頁）

- `site-config.js` 新增 `UPDATE_FORM_URL`，**留空＝相關按鈕全部隱藏**（沿用既有慣例，未設定不會壞）。檔頭「三個外部連結」的註解要同步改成四個。

## 二、維護追蹤（三件工具）

### 1. 後台儀表板加強

在現有總覽儀表板（已有「近 7 天有更新」「缺資料清單」）新增：

- **待審更新申請數**：總管理員看全會、組長看本組，有待審就標紅，點了跳到更新待審區。

### 2. Google 試算表追蹤

**表單回應試算表本身就是維護紀錄**——誰、何時、送了什麼，Google 自動記好。比照來賓 CRM 的作法，建立後手動加三欄：**審核狀態／審核人／完成日**，組長核可後回來勾。

### 3. 催收分享訊息產生器

**既有的要先改**：後台「缺資料清單」現在就會產生整包 LINE 催收訊息，但文案是「請直接把缺的內容回覆給網管，由網管統一更新」——與新流程直接打架。要改成附上 `UPDATE_FORM_URL`、引導自助更新（未設定 `UPDATE_FORM_URL` 時保留舊文案，維持留空不會壞的慣例）。

## 三、Bug 回報區（站上按鈕 → 佇列 → 排程整理成升級建議）

### 1. 流程

```
任何人在網站上看到問題
  │ 點頁腳「回報問題」→ 小視窗：類別＋嚴重程度＋描述（自動帶入頁面/瀏覽器/資料版本）
  ▼
瀏覽器直接 POST Worker /report（公開端點、無密鑰；同 /views 模式）
  │ 限流、honeypot、清洗、樂觀鎖
  ▼
data/_bugs.json（回報佇列，上限 50 則）
  ▼
排程 GitHub Action（每日一次）檢查：待處理 ≥5 則，或最舊一則滿 3 天？
  │ 否 → exit 0；是 ↓
  ▼
tools/digest-bugs.mjs 規則式整理：分組 → 評分（嚴重程度 × 回報數）→ 排序 → 對應建議
  ├─ 產出 data/_bug-digest.json（後台儀表板讀這份）
  ├─ 開 GitHub Issue「升級建議 YYYY-MM-DD」（排序清單＋原始回報＋建議動作）
  │    └─ GitHub 自動寄 Issue 通知信給 watch 這個 repo 的網管（Email 通知零設定）
  └─ 從 _bugs.json 移除已整理的回報（內容留存在 digest 與 Issue）
```

### 2. 回報按鈕與表單（app.js＋styles.css）

- 入口：公開各頁（index、visitor 等）頁腳一條低調的「**回報問題**」連結，點開小視窗（不跳頁、不打斷瀏覽）。
- 欄位：

| 欄位 | 型式 | 必填 |
|---|---|---|
| 類別 | 二選一：網站功能問題／改善建議 | ✔ |
| 嚴重程度 | 三級：完全不能用／很不方便／小瑕疵（「改善建議」類固定為建議，不選嚴重度） | 功能問題必選 |
| 發生了什麼 | 多行文字，≤1000 字 | ✔ |
| 稱呼（選填） | 短文字，方便後續詢問細節 | － |
| 自動帶入 | 發生頁面路徑、瀏覽器 UA、資料版本（`data-version.txt` 的值） | 系統 |

- 視窗內註明：「**成員資料有誤請改用『更新我的資料』表單**，這裡只收網站問題與建議」——把資料錯誤導去正確的通道（決策 8）。
- 防濫用配合：一個 CSS 隱藏的 honeypot 欄位（有值即靜默丟棄）＋開啟視窗到送出的最低停留秒數。
- 送出成功顯示「已收到，謝謝回報」；佇列滿（`bugs_full`）或被限流時顯示「回報量較大，請稍後再試」。

### 3. Worker 端：/report 公開端點

**為什麼無密鑰**：回報按鈕在公開頁面的 JavaScript 裡，藏不住任何密鑰（`WORKER_URL` 本來就公開寫在 app.js）。這與 `/views` 是同一種端點：公開、無密碼，靠 Origin 檢查（帶 Origin 必須等於 `ALLOWED_ORIGIN`）與防濫用機制守住。差別是 `/report` 會寫 GitHub，所以防護比 /views 更嚴：

| 防線 | 設計 |
|---|---|
| 開關 | 環境變數 `REPORTS_ENABLED` 未設＝整條通道關閉（fail-closed，比照 INTAKE_SECRET 未設即關的哲學） |
| 限流 | 同 IP 15 分鐘 **5 則**（比 intake 的 20 嚴——回報不該高頻），KV key 用獨立前綴 `bug:`，不污染登入／intake 計數，並留意 KV 免費額度（/views 的教訓） |
| honeypot | 隱藏欄有值＝回 ok 但靜默丟棄（不給灌水者訊號） |
| 清洗 | `sanitizeBugReport()`：類別與嚴重度走白名單、描述 ≤1000 字、頁面只留站內路徑（去 query／hash）、UA ≤300 字、稱呼 ≤80 字 |
| 識別碼 | `bid` 由伺服器產生（`b_` 前綴） |
| 容量 | `MAX_BUGS=50`，滿了回 `bugs_full`；**寫回前序列化大小檢查**（同 /update 的防線；純文字佇列正常遠小於上限） |
| 寫入 | 樂觀鎖 read-modify-write，最多嘗試 5 次，fail-closed——與 intake 同一套 |

注意：回報通道**沒有** Google 試算表那層留底——被限流或佇列滿時回報就是丟了（前端有告知）。這是站上按鈕相對表單的固有取捨，已接受；嚴重問題總會有人再報一次。

白名單三處同步（與 `_updates` 一起改）：

1. `DATA_PATH_RE` 加 `_bugs`（Worker 與 admin.js 兩份都要）。
2. `canWriteDataFile`：`_bugs.json` **僅 owner 可寫**（用途只有網管從後台刪垃圾回報；組長不需要動它）。
3. `checkDataFileBody`：`_bugs.json` 須為陣列、每筆 `bid` 過 `MEMBER_ID_RE`、類別／嚴重度欄位型別正確、筆數 ≤50。
4. `data/_bug-digest.json` 是排程 Action 的產出物，**不加入**可發布白名單——Worker 拒寫，唯一的寫入者是 Action（與 data.js 只能由 Action 產生同一哲學）。

### 4. 排程整理（.github/workflows/digest-bugs.yml ＋ tools/digest-bugs.mjs）

**觸發**：cron 每日一次（建議 21:00 UTC＝台灣早上 5 點，避開使用高峰）＋ `workflow_dispatch` 手動觸發。每次執行先檢查條件——`data/_bugs.json` 待處理 **≥5 則**、或**最舊一則距今超過 72 小時**——不成立就 exit 0（與 sync.yml「沒有變更，不需提交」同款的安靜收場）。

**規則式整理**（零 AI、零金鑰、結果可預期）：

1. **分組**：同（類別＋發生頁面）歸為一組——同頁同類的回報視為同一件事的多次回報。
2. **評分**：`分數 ＝ 嚴重程度權重 × 回報則數`。權重：完全不能用 3、很不方便 2、小瑕疵／改善建議 1。回報則數就是「重要程度」——越多人報，越重要。
3. **排序＋建議**：依分數由高到低排列；分數 ≥6 →「建議立即安排修復」、3〜5 →「排入下次更新」、<3 →「觀察，累積後再評估」。同分以最舊回報優先。

**產出三件事**：

- 寫 `data/_bug-digest.json`：本期排序清單＋產出時間＋對應的 Issue 編號，保留最近幾期供後台顯示。
- 開 GitHub Issue「升級建議 YYYY-MM-DD」：排序清單、每組附原始回報列點（描述／頁面／時間）、建議動作。workflow 的 `permissions` 區塊要**同時宣告 `contents: write`（push 移除已整理回報用）與 `issues: write`（開 Issue 用）**——GitHub 的 permissions 一經宣告，沒列出的權限一律歸零，漏了 contents 會讓 push 403（sync.yml 就是為 push 宣告了 contents: write）。用內建 `GITHUB_TOKEN`，**不動 Worker 那顆只有 Contents 權限的 fine-grained token**——這正是把佇列放 repo、由 Action 開 Issue 而不是讓 Worker 直接開 Issue 的原因：Worker 的權杖範圍不用放大。
- 從 `_bugs.json` 移除已整理的回報後 commit＋push（內容已留存在 digest 與 Issue，佇列保持乾淨、50 則上限不會被舊帳佔滿）。

**Email 通知**：GitHub 開 Issue 時會自動寄通知信給 watch 這個 repo 的帳號——網管把 repo 設為 Watch 即滿足「Email 通知網管」，**零 SMTP 設定**。若日後要寄到非 GitHub 信箱，再在 Action 加寄信步驟（需 SMTP secrets），列為選配。

**併發與遞迴**：

- push 用內建 `GITHUB_TOKEN`，不會觸發其他 workflow（GitHub 防遞迴，與 sync.yml 同性質）；`_bugs.json`／`_bug-digest.json` 的變更即使觸發 sync 也是無 diff、exit 0。
- Action 移除回報要 push main 的同時，Worker 可能正好 append 新回報：Worker 端樂觀鎖會 stale 重試拿到新版；Action 端 push 被拒就比照 sync.yml——fetch＋reset 後重做再 push，最多重試數次。兩邊各自重試、互不覆蓋。

### 5. 後台儀表板（admin.js）

- 「**待整理回報 N 則**」：即時讀 `_bugs.json` 的筆數，點開可展開原始回報；owner 可刪除垃圾回報（走既有 /publish 寫回 `_bugs.json`，這就是 `_bugs` 要進發布白名單的原因）。
- 「**最新升級建議**」：讀 `_bug-digest.json`，顯示最近一期的排序清單與對應 GitHub Issue 連結。

## 四、安全與防護（全部沿用現有原則）

| 原則 | 在本設計的落點 |
|---|---|
| fail-closed | 密鑰未設＝更新通道關閉；`REPORTS_ENABLED` 未設＝回報通道關閉；`_index.json` 讀不到＝拒收；驗證失敗＝整筆退回，不靜默修補 |
| 密鑰不進瀏覽器 | `INTAKE_SECRET` 只存在 Apps Script 伺服器端與 Cloudflare；回報通道乾脆不設密鑰（公開 JS 藏不住），改靠限流＋honeypot＋容量上限＋開關 |
| 收件口與編輯權隔離 | `/update` 只能寫 `_updates.json`、`/report` 只能寫 `_bugs.json`，都拿不到 session、寫不到分組檔——與 /intake 同樣的隔離 |
| 樂觀鎖 | 三條收件通道都走 blob sha＋stale 自動重試；後台發布端 stale 則回 `stale_base` 錯誤擋下、由人重來——兩端機制不同，但結論一致：不互蓋 |
| 限流與 KV 隔離 | `update:`、`bug:` 各自獨立前綴；灌爆任一通道不影響登入 |
| 伺服器產識別碼 | `uid`／`bid` 伺服器產生；成員 id 由後台審核時對應，外部資料無法指定 |
| 照片不提前落地 | 待審階段內嵌 data: URL，核可發布後才變 images/ 實體檔 |
| 產出物只由 Action 寫 | data.js、m/、roster.csv 如既往；`_bug-digest.json` 同樣只有 Action 能寫，Worker 拒收 |
| 權杖範圍不放大 | Worker 的 fine-grained token 維持只有 Contents 權限；開 Issue 用 Action 內建 `GITHUB_TOKEN` 的 `issues: write` |

資料限制總表：

| 項目 | 上限 | 適用 |
|---|---|---|
| 一般文字欄／清單項 | 400 字（intake 的預設上限；姓名與職稱 80、公司 120、網址 300） | /update 比照 |
| 清單欄 | 12 項 | /update 比照 |
| 單張照片 | base64 ≤700KB（Apps Script 端 ≤650KB 留餘裕） | /update 比照 |
| 單筆照片加總 | base64 ≤2MB（只算照片，文字另計；intake 維持 3MB——收嚴的原因是佇列檔發布時整檔再 base64 膨脹 4/3，見「待審區資料格式」） | /update |
| 佇列筆數 | `_updates`／`_bugs` 各 50 筆 | 滿了回 full 錯誤 |
| 佇列檔大小 | 寫回前以發布用 base64 長度自檢 ≤3.5MB（與 `MAX_DATA_B64_CHARS` 同一把尺；/intake 目前沒有這道、新端點必加） | /update、/report |
| 資料檔發布上限 | base64 4MB（`MAX_DATA_B64_CHARS`，**只在 /publish 端檢查**）——收件端的 3.5MB 自檢就是為了永遠不觸到這條 | /publish |
| Bug 描述 | 1000 字 | /report |

## 六、風險與已接受的取捨

| 風險 | 因應 | 狀態 |
|---|---|---|
| 冒名送更新 | 組長審核＋email 佐證＋兩段式生效；分會人人互識，錯誤會被認出 | 已接受（與「新夥伴自報姓名」同級） |

## 附錄：與既有機制的對照速查

| 既有機制 | 本設計的對應 |
|---|---|
| 新夥伴表單（createNewMemberForm） | 會員更新表單（createMemberUpdateForm） |
| `/intake` 端點（Apps Script 中繼、有密鑰） | `/update` 端點（同模式） |
