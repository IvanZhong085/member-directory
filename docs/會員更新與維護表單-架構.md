# 會員資料更新與維護表單・架構規劃

> 本文件是「會員自助更新資料」與「名錄維護追蹤」兩件事的架構規劃，經問答定案後撰寫。
> 目標讀者：要實作這個功能的人（或 AI），以及日後想了解「為什麼這樣設計」的維護者。
> 尚未實作——這是規劃文件，不是使用說明。

---

## 決策記錄（問答定案）

| # | 問題 | 決定 |
|---|------|------|
| 1 | 表單給誰用、做什麼 | **兩者都要**：會員自助更新自己的資料＋組長的維護追蹤 |
| 2 | 承載工具 | **Google 表單**（會員最熟悉、免帳密，沿用新夥伴表單管線） |
| 3 | 身分確認 | **自報姓名＋組長審核**（分會成員彼此認識，組長把關） |
| 4 | 生效方式 | **進待審區、組長核可後發布**（比照新夥伴待認領的兩段式） |
| 5 | 開放欄位 | **文字＋照片都開放**（形象照／名片／商品照） |
| 6 | 留空語意 | **留空＝不更動**（只填想改的欄位） |
| 7 | 維護追蹤形式 | **後台儀表板加強＋Google 試算表追蹤＋催收分享訊息產生器** |

### 為什麼這個組合對會員最簡單

- 會員端只有一件事：**點連結 → 填想改的欄位 → 送出**。不用帳號密碼、不用學新工具，和報名參訪、新夥伴申請的體驗一致。
- 把關成本放在組長端，而組長本來就在後台工作；審核一筆更新比代打整張卡快得多。
- 錯誤資料不會直接上站（兩段式），冒名申請靠「組長認得自己組員」擋下——這是分會（實體組織、人人互識）才有的低成本身分驗證。

## 整體架構

沿用現有「新夥伴申請」已驗證可行的管線，**平行複製一條**，不共用佇列：

```
會員（免帳密）
  │ 填 Google 更新表單（只填想改的欄位）
  ▼
表單回應試算表 ←──────────────┐（永遠留底，送失敗可人工補救）
  │ onUpdateFormSubmit 觸發器  │
  ▼                           │
Apps Script（伺服器端，密鑰不外洩）
  │ POST {secret, update:{…}} 到 Worker /update
  ▼
Cloudflare Worker /update（限流、清洗、樂觀鎖）
  │ 追加一筆到 data/_updates.json（更新待審區）
  ▼
組長登入後台 → 「更新待審」清單 → 變更前後對照 → 核可／退回
  │ 按「發布到網站」（走既有 /publish，權限與版本偵測不變）
  ▼
data/<組代號>.json 更新（蓋 updatedAt）＋ _updates.json 移除該筆
  ▼
GitHub Action（sync.yml）→ data.js / m/ 分享頁 / roster.csv 全自動重建
```

對照現有機制：`data/_pending.json`（新夥伴待認領）怎麼運作，`data/_updates.json`（更新待審）就怎麼運作。差別只在：pending 是「整個人新增」，updates 是「指定成員的部分欄位變更」。

### 為什麼開新佇列檔，不共用 `_pending.json`

- `_pending.json` 有 `MAX_PENDING=50` 的容量上限，且與新夥伴申請共用同一個限流池；混用會互相排擠額度。
- 兩種資料語意不同（新增 vs 部分變更），共用一檔會讓認領 UI 和驗證規則都長出分支。
- 代價是 Worker 要把新路徑加進三處白名單（見下方「Worker 端」），一次改齊即可。

## 一、會員自助更新（表單 → 待審 → 核可）

### 1. Google 表單設計

**身分區**（比對用，不做技術驗證）：

| 題目 | 型式 | 必填 |
|---|---|---|
| 你的分組 | 下拉選單（12 組，含代號＋組名） | ✔ |
| 你的姓名 | 簡答 | ✔ |
| 所屬公司（同名時區辨用） | 簡答 | － |

**更新區**（與名錄欄位一一對應，全部選填；題目文字需與程式的別名表同步）：

行業／職稱、服務項目、適合引薦對象、我有…、我要…、25 秒自我介紹 Slogan、所屬公司、主要營業項目、公司網站——與新夥伴表單的 10 題文字題同一套題目文字，直接沿用 `NEWMEMBER_Q` 的標題與別名機制。

**照片區**（上傳題，全部選填）：形象照 1 張、名片 1 張、商品照最多 5 張。

表單說明文字必須寫明兩條規則：

> 「**只填你想更改的欄位，沒填的欄位維持現狀**。若要清空某欄，請在該欄填『無』，組長審核時會處理。」

已知取捨：

- Apps Script 無法程式化建立上傳檔案題，三個照片題要**手動**在表單編輯頁加上，標題須與程式一字不差（與新夥伴表單相同的限制與作法）。
- 表單含上傳題時 Google 強制填答者登入 Google 帳號——順勢**開啟 email 收集**（`setCollectEmail`），把填答者 email 一併送進待審資料，給組長多一層「是不是本人」的佐證。這是新夥伴表單沒做、更新表單要做的差異點。

### 2. Apps Script（tools/google-form.gs 擴充）

新增（與新夥伴表單平行、互不干擾）：

- `createMemberUpdateForm()`：建表單＋回應試算表＋掛觸發器。防重跑用**新的**指令碼屬性鍵 `UPDATE_FORM_EDIT_URL`（`guardAlreadyCreated_` 直接重用）。
- `onUpdateFormSubmit(e)`：組 payload、POST 到 Worker `/update`。觸發器名稱獨立，不與 `onNewMemberSubmit` 混用。
- `checkUpdateFormSetup()`：比照 `checkNewMemberSetup` 的診斷手法（故意送空 payload，用錯誤碼區分密鑰不符／未設定／線路通）。

直接重用、不必重寫：標題正規化與別名對應（`normTitle_`／`pickByTitle_`）、整條照片管線（`driveImageDataUrl_` → `thumbBlob_` → `blobToDataUrl_`，含 HEIC 轉檔與 650KB 上限）、照片歸檔（歸檔目的地可共用，子資料夾改成 `會員更新照片/`）、`RELAY_URL`／`INTAKE_SECRET` 指令碼屬性機制。

payload 格式（**只含有填的欄位**——留空＝不更動就是在這裡實現的）：

```json
{
  "secret": "<INTAKE_SECRET>",
  "update": {
    "group": "A1",
    "name": "王小明",
    "company": "小明企業",
    "respondentEmail": "xxx@gmail.com",
    "fields": {
      "services": "冷氣保養\n舊機回收",
      "tagline": "新的一句話標語",
      "image": "data:image/jpeg;base64,…"
    }
  }
}
```

送出失敗（Worker 掛掉、密鑰錯）時只寫 Logger，**回應仍留在試算表**當備份，可人工補登——與新夥伴表單相同的保底設計。

### 3. Worker 端（worker/publish-relay.js 擴充）

新增 `/update` 端點，行為完全比照 `/intake`，差異只有目標檔與資料形狀：

| 項目 | 設計 | 依據 |
|---|---|---|
| 認證 | 共用 `INTAKE_SECRET`（兩條通道信任等級相同：都只有 Apps Script 伺服器端持有）。未設定＝整條通道關閉（fail-closed） | 沿用 /intake 的密鑰哲學；若日後要單獨關閉更新通道，再拆成獨立 `UPDATE_SECRET` 即可 |
| 限流 | 同 IP 15 分鐘 20 份，**KV key 用獨立前綴 `update:`**，不污染登入與 intake 的計數 | /views 灌爆 KV 額度的教訓：公開端點必限流、必隔離 |
| 清洗 | 新寫 `sanitizeUpdate()`：白名單欄位、文字 400 字、陣列 12 項、單張照片 base64 ≤700KB、整份 ≤3MB、website 須 http(s)、`group` 必須存在於 `_index.json` 的組代號、`name` 必填 | 比照 `sanitizeApplicant` 的所有既有限制 |
| 識別碼 | `uid` 由**伺服器**產生（`u_` 開頭），外部不能指定；表單資料裡**沒有任何欄位能決定成員 id**（id 會變成 `m/<id>.html` 檔名，有路徑穿越風險，對應交給後台審核時做） | pid 由伺服器產生的同一原則 |
| 寫入 | 讀 `data/_updates.json` 現行內容＋blob sha → 追加 → 帶 sha 寫回；stale 就重讀重試最多 5 次，全失敗回錯不靜默覆蓋。上限 `MAX_UPDATES=50`，滿了回 `updates_full` | /intake 的樂觀鎖 read-modify-write 迴圈，原樣照抄 |

路徑白名單要**同步改齊三處**（漏一處就是發布被拒或驗證缺口）：

1. `DATA_PATH_RE`（Worker 與 admin.js **各有一份**，兩邊都要加 `_updates`）。
2. `canWriteDataFile`：`_updates.json` 比照 `_pending.json` 對所有組長開放寫入（核可後要從清單移除該筆）。這延續現有的知情取捨——組長之間看得到彼此組的待審項目，真正的把關在「核可寫入分組檔」那一步，而那一步的路徑權限不變。
3. `checkDataFileBody`：新增 `_updates.json` 的結構驗證——必須是陣列、每筆 `uid` 過 `MEMBER_ID_RE`、`group` 為字串、`fields` 為物件且陣列欄位型別正確、筆數 ≤50。壞資料會凍結全站產線，所以擋在 Worker。

### 4. 待審區資料格式（data/_updates.json）

```json
[
  {
    "uid": "u_a1b2c3d4",
    "at": "2026-08-09T12:34:56.000Z",
    "group": "A1",
    "name": "王小明",
    "company": "小明企業",
    "respondentEmail": "xxx@gmail.com",
    "fields": {
      "services": ["冷氣保養", "舊機回收"],
      "tagline": ["新的一句話標語"],
      "image": "data:image/jpeg;base64,…"
    }
  }
]
```

- `fields` 只含會員有填的欄位；多行文字在 Worker 端切成陣列（與 intake 相同）。
- 照片在待審階段一律以 `data:` URL 內嵌，**核可並發布後**才由既有的 extract-inline-photos 產線轉成 `images/` 實體檔——未核可的申請不會在 repo 留下孤兒圖檔。
- 檔案大小注意：`_pending.json` 實測一筆含照片的申請就 1.5MB，單檔 base64 上限 4MB。`MAX_UPDATES=50` 是筆數上限，實際瓶頸是照片；若佇列常態性塞車，優先手段是催組長清佇列，不是調大上限。

### 5. 後台審核 UI（admin.js 擴充）

比照「新夥伴待認領區」整套渲染與事件模式，新增「**更新待審區**」：

- **清單**：每筆一張卡，顯示申請人自報的組別＋姓名＋公司＋email＋申請時間。
- **成員對應**：後台用「組別＋姓名」在現有名錄找人——唯一命中就預選；同名多筆或找不到時，卡片顯示該組成員下拉選單請組長**手動指定**。表單資料永遠不直接決定成員 id。
- **變更前後對照**：對 `fields` 裡的每個欄位，顯示「現在的值 → 申請的新值」。這是審核 UI 的核心——組長一眼看出這筆改了什麼，沒改的欄位不出現。
- **操作**：「核可」＝把 `fields` 逐欄套進該成員卡＋蓋 `updatedAt`＋從待審清單移除；「退回」＝僅從清單移除（表單回應試算表永遠留底，不怕誤刪）。都是本機草稿，**要按「發布到網站」才真正生效**（兩段式不變）。
- **權限**：viewer 整區隱藏；組長預設只看到自己組的待審申請（依 `group` 欄位過濾），總管理員看全部並可改派組別（處理會員選錯組的情況）。
- **一致性**：undo 快照與草稿目前寫死為 `{data, pending}`，必須擴充成 `{data, pending, updates}`，否則核可後按「復原」會遺失待審狀態；發布 payload 的逐字比對、`baseHashes` 版本偵測，都要把 `_updates.json` 一併納入（作法與 `_pending.json` 完全相同）。
- **序列化**：核可寫入分組檔時走既有的 groupBody 序列化與鍵順序，避免產生無意義 diff 或壞掉合併產線。

清空欄位的處理：會員在表單填「無」時，該欄會以字串「無」出現在對照畫面，由組長核可時人工把該欄清掉——規則簡單、不需要程式猜語意。

### 6. 前台入口（site-config.js＋成員內頁）

- `site-config.js` 新增 `UPDATE_FORM_URL`，**留空＝相關按鈕全部隱藏**（沿用既有慣例，未設定不會壞）。
- 成員內頁的「分享這位夥伴」工具列加一顆「**更新我的資料**」按鈕，直接開表單。會員最常到達自己內頁的路徑（自己的 QR code、分享連結）就是最自然的更新入口。
- 後台總覽儀表板加「會員更新表單」捷徑（比照來賓報名表單捷徑）。

## 二、維護追蹤（三件工具）

### 1. 後台儀表板加強

在現有總覽儀表板（已有「近 7 天有更新」「缺資料清單」）新增：

- **待審更新申請數**：總管理員看全會、組長看本組，有待審就標紅，點了跳到更新待審區。
- **太久沒更新清單**：依 `updatedAt` 排序，超過門檻（建議 6 個月，做成可調常數）標示；`updatedAt` 為空（從未更新過）排最前。與既有「缺資料清單」互補：一個催「有欄位空著」，一個催「資料可能過期」。

### 2. Google 試算表追蹤

**表單回應試算表本身就是維護紀錄**——誰、何時、送了什麼，Google 自動記好。比照來賓 CRM 的作法，建立後手動加三欄：**審核狀態／審核人／完成日**，組長核可後回來勾。

分工：`roster.csv` 鏡像試算表看「現況」（全會名冊長怎樣），更新回應試算表看「歷程」（誰在維護資料、審到哪）。兩份都是唯讀鏡像＋人工註記，不迴寫網站。

### 3. 催收分享訊息產生器

在後台「太久沒更新清單」與「缺資料清單」的每位成員旁加「**產生催收訊息**」：一鍵複製 LINE 訊息，內容自動帶入——

> 「○○夥伴你好！名錄上你的資料已經 N 個月沒更新囉（缺：商品照片、我要…）。花 2 分鐘用這個表單更新一下：<表單連結>。只要填想改的欄位就好！」

組長複製貼給組員即完成催收。實作上比照 spotlight 的文案模板模式（模板字串＋成員資料代入），不需要新頁面。

## 三、安全與防護（全部沿用現有原則）

| 原則 | 在本設計的落點 |
|---|---|
| fail-closed | 密鑰未設＝通道關閉；`_index.json` 讀不到＝拒收；驗證失敗＝整筆退回，不靜默修補 |
| 密鑰不進瀏覽器 | `INTAKE_SECRET` 只存在 Apps Script 伺服器端與 Cloudflare，公開網頁裡沒有任何密鑰 |
| 收件口與編輯權隔離 | `/update` 只能寫 `_updates.json`，拿不到 session、寫不到分組檔——與 /intake 同樣的隔離 |
| 樂觀鎖 | 收件寫入與後台發布都走 blob sha＋stale 重試，會員送更新撞上組長發布不會互蓋 |
| 限流與 KV 隔離 | 獨立 `update:` 前綴、同窗 20 份/IP，灌爆更新通道不影響登入 |
| 伺服器產識別碼 | `uid` 伺服器產生；成員 id 由後台審核時對應，表單資料無法指定 |
| 照片不提前落地 | 待審階段內嵌 data: URL，核可發布後才變 images/ 實體檔 |
| 產線保護 | `checkDataFileBody` 擋壞資料於 Worker，避免一個壞檔凍結全站 data.js |

資料限制總表（與 intake 一致）：文字欄 400 字、清單欄 12 項、單張照片 base64 ≤700KB（Apps Script 端 ≤650KB 留餘裕）、單筆總量 ≤3MB、佇列 50 筆、單檔 4MB。

## 四、實作清單（分三階段）

### 階段一：自助更新最小可用（核心）

| 檔案 | 改動 |
|---|---|
| `tools/google-form.gs` | 新增 `createMemberUpdateForm` / `onUpdateFormSubmit` / `checkUpdateFormSetup`＋題目表與別名表；開啟 email 收集 |
| `worker/publish-relay.js` | 新增 `/update` 端點、`sanitizeUpdate`、`MAX_UPDATES`；`DATA_PATH_RE`／`canWriteDataFile`／`checkDataFileBody` 三處加 `_updates` |
| `admin.js` | 更新待審區渲染與核可／退回；成員對應（組別＋姓名，含手動指定）；變更前後對照；snapshot／草稿／發布 payload 納入 `_updates.json`；`DATA_PATH_RE` 同步 |
| `site-config.js` | 新增 `UPDATE_FORM_URL`（留空隱藏） |
| `app.js`（成員內頁） | 「更新我的資料」按鈕 |
| 手動設定（一次） | 表單加 3 個上傳題；Cloudflare 重貼 Worker 程式碼；`site-config.js` 貼表單網址後發布 |

### 階段二：維護追蹤

| 檔案 | 改動 |
|---|---|
| `admin.js` | 儀表板加「待審更新申請數」「太久沒更新清單」；催收訊息產生器（模板＋一鍵複製） |

### 階段三：試算表追蹤（純手動設定）

回應試算表加「審核狀態／審核人／完成日」三欄，README 補充操作說明。

不需要動的：`tools/build-data.mjs`（`_updates.json` 不在 `_index.json` 清單、天然不進合併）、`csv-schema.js`（沒有新增成員欄位）、`sync.yml`（寫 `_updates.json` 會觸發一次 Action 但無 diff、exit 0 收場，成本可接受）。

## 五、風險與已接受的取捨

| 風險 | 因應 | 狀態 |
|---|---|---|
| 冒名送更新 | 組長審核＋email 佐證＋兩段式生效；分會人人互識，錯誤會被認出 | 已接受（與「新夥伴自報姓名」同級） |
| 佇列被灌爆 | IP 限流 20/15min＋上限 50 筆＋fail-closed；試算表留底可人工補救 | 已防護 |
| `_updates.json` 因內嵌照片變大 | 單筆 3MB／單檔 4MB 上限；催組長清佇列優先於調大上限 | 已知，監控即可 |
| 表單題目文字被改動導致欄位對不上 | 沿用別名表機制；README 註明「改題目須同步改程式」 | 與新夥伴表單同級 |
| 上傳題無法程式建立 | 手動加題，`checkUpdateFormSetup` 提供診斷 | 與新夥伴表單同級 |
| 組長互見彼此組的待審申請 | 前端依 group 過濾顯示；伺服端寫入分組檔的權限不變，越權核可仍被 `/publish` 擋下 | 已接受（與 `_pending` 同級的知情取捨） |
| 會員選錯組別 | 總管理員可在待審卡改派組別 | 已處理 |
| 同名成員 | 「公司」欄輔助區辨＋組長手動指定成員 | 已處理 |

## 附錄：與既有機制的對照速查

| 既有機制 | 本設計的對應 |
|---|---|
| 新夥伴表單（createNewMemberForm） | 會員更新表單（createMemberUpdateForm） |
| `/intake` 端點 | `/update` 端點 |
| `data/_pending.json`（待認領） | `data/_updates.json`（待審） |
| `pid`（`p_` 前綴） | `uid`（`u_` 前綴） |
| 後台「待認領區」＋認領 | 後台「更新待審區」＋核可 |
| 認領＝整個人加入分組 | 核可＝部分欄位套用＋蓋 `updatedAt` |
| `MEMBER_FORM_URL` | `UPDATE_FORM_URL` |
| 來賓 CRM 試算表＋手動追蹤欄 | 更新回應試算表＋審核狀態欄 |
